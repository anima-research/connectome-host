# Setting up a resident

This guide is for you, an agent who sets up a resident on the machine you run on. The person sits at that machine's terminal. A resident is the person's agent. This install runs it as a service, with a memory of its own, and it talks on Discord. You're most likely connectome-host's own setup agent, which `connectome setup discord` started. You run commands with `setup--run`, and you ask for secrets with `setup--ask_secret`. If you're another harness, first read "With another harness" at the end.

Read the guide a section at a time. `grep -n '^## ' '<this file>'` lists its sections with their line numbers, and `sed -n '<first>,<last>p' '<this file>'` reads one. Each section is under 8 KiB. So a read of a whole section of ordinary text comes back whole. Only output that is dense in characters that JSON escapes can still be cut.

Below, `<dir>` is the working directory that your prompt names, where your commands run. `<host>` is the host's package directory, the one that holds this guide's `docs/`. `connectome` names the install's own command, `./connectome-host/connectome` from `<dir>`. Each line that you give the person to type must work as you give it, and so must the line that brings them back to setup. So spell the install's command as your prompt does. In a shell command, put each path or value that you fill in between single quotes, as this guide's examples do. A space or a shell character in it then stays part of it. Write each `'` inside such a value as `'\''`: a folder named `Alice's export` goes in as `'Alice'\''s export'`.

**What setup did before you started,** so don't do it again or undo it:
- It said where the resident will live: `<dir>`. That is the directory setup was run in, when that directory was empty or already setup's, holding `.setup` or an install record. Otherwise it is `~/resident`, which setup made if it wasn't there. When an install's own command runs setup, `<dir>` is the directory that holds that install.
- Setup can show the line that makes the resident a user of its own: on Linux with systemd and sudo, when setup runs as a user other than `connectome`, the name that the line gives. Where it could show that line, on the run that began this setup, it said what a shell would reach in this account, showed the line, and asked whether to go on here. Once the install's record is there, setup no longer asks this. Your prompt gives you that line, or "none" where setup had none to show ("The resident's shell"). Elsewhere, this run asked nothing about the user that the resident runs as. Your prompt names that user, and you run as that user. Setup didn't ask whether the resident gets a shell: the person decides that with you ("The resident's shell").
- On Linux, where linger was off for that user, setup showed the person the root line that turns linger on. It said that they, or whoever administers the machine, can run that line at any time before the resident goes live. Then it went on, and it asked nothing. Your prompt gives you that line, or "none" where linger was on or the machine has no systemd ("The read-back").
- It checked Bun and Node, then installed connectome-host in `<dir>` with Bun, along with discord-mcpl (`node_modules/@animalabs/discord-mcpl`). It installed nothing for a shell.
- It made the install root, `<dir>/connectome-host`. The root holds the releases, `start.js` (the entry that the service runs), the install's record and the `connectome` command. Updates manage what's there, so write nothing of yours under it.
- It started the installed host once, with a test setup that calls no model, to see that it starts.
- It checked an API key with one real call to your model. It keeps the key in `<dir>/.env`, which this user alone can read. The resident uses that key, except in three cases. The person can choose otherwise. `.env`, or an earlier source ("Secrets"), can hold `ANTHROPIC_AUTH_TOKEN` or `ANTHROPIC_OAUTH_CREDENTIALS_FILE`. Or the shell that a host is started from by hand can export one of them. In the last two cases, the host signs in through OAuth instead. A host takes another `ANTHROPIC_API_KEY` where the shell that it's started from by hand exports one, or where an earlier source sets one ("Secrets").
- It made `<dir>/data`, the resident's data directory, where its memory will live. It also made `<dir>/.setup`, which is yours: it holds your conversation and the names of the secrets stored. An install that already had a data directory keeps it, and the install's record, `<dir>/connectome-host/install.json`, names it as `dataDir`. Where that is another place, use it wherever this guide writes `<dir>/data` or `data`.

**What's left,** in order, each with its section:
1. Talk with the person about who the resident is: its name, and whether it continues a history. Ask about the history at this step ("Working with the person").
2. Decide with the person whether the resident gets a shell, and on a yes, install it ("The resident's shell").
3. Set up the Discord bot, its invite and where it can be reached ("Discord" and "Discord's settings").
4. Bring in that history, if there is one ("Importing a history").
5. Give one read-back of everything, its defaults included. One yes to it covers writing the recipe, starting the service, `connectome doctor` and `SETUP.md` ("The read-back"). Then follow "The recipe", "The recipe's servers", "What the resident may do to itself", "Going live", "SETUP.md" and "SETUP.md, its other lines".
6. The person's own hello ("Going live").
7. After the hello, whatever came of it, tell them plainly that you aren't the resident. Then offer backups, now or later ("After the hello", "Backups", "The restore check" and "SETUP.md's backups line").
8. Once they have nothing more, call `setup--finished` ("After the hello").

"Secrets" applies to every step. Read "Gateways and other providers" and "Gotchas" when they apply.

## Working with the person

The person may not be technical. Ask in plain words, one question to a message, and wait for its answer before starting the next step. When you ask them to confirm something, such as a read-back, end the message with that question. Start the next step in your next message. Decide the mechanics yourself (paths, versions, the service), check each step and tell them what you saw, and move at their pace. Ask your questions in the conversation.

**Tell them first how you work, then keep to it.** Each command that you run with `setup--run` is shown to them whole as it starts. But its output comes back to you alone, so tell them what it showed. Two commands are the exception: `connectome service install` and `connectome shell install`, the install's commands that change the machine. When each of them ends, the person's screen shows what it printed too. But what a program run by such a command prints, such as Bun's lines in `shell install`, still reaches you alone. So when a shown command fails on what a program printed, tell the person what that output said. Run a command that only reads, such as a look at a file, without asking. Run `connectome doctor` without asking too, though its connection to the host closes the connection of any other connectome command, such as a `connectome send` that waits for a reply. **A yes belongs to a decision:** the shell, an import, the read-back that ends in going live, backups, and anything irreversible or public. The yes covers what this guide's step for that decision names, with its files and its commands. So you make those without asking again, and you say what you wrote and where. Outside those steps, show the command and wait for their yes before a command that installs, builds or trusts software, or that changes anything outside `<dir>`. Ask again before the next such command, even when it serves the same aim. Before you change something that they've already agreed to, such as the recipe or `SETUP.md`, show the change itself, then make it. Once you've read this, and before your next command, tell them this as it is: each command is shown as it starts and doesn't wait for them; what only reads runs without asking; you stop for their yes at each decision above, and, outside those, before installing, building or trusting software or changing anything outside `<dir>`; and you show a change to something they agreed to before you make it. Promise no more than that, such as a question before every command.

**Name a cause only when you've seen it,** in a log line, a run or the code. Otherwise, tell them what you saw and that the cause isn't known. Never write a guess into a file as if it were known.

**When you propose something that this guide and the docs it points to don't describe,** say so. Before they agree, name every cost that you know, including what `connectome doctor` will then show.

**When they ask what something means, answer that,** and don't ask for the decision in the same message. Any decision can wait until they're ready: say what waiting costs, if anything, and let them come back to it.

**Commands the person runs themselves.** A root line is theirs to run. So is a line that writes a secret that they type, such as the backup's password. For such a line, ask them to open a second terminal and to leave this one open, since this conversation is in it. Give them the lines whole. In an example that they might copy, write a placeholder that nobody could take for a real value, such as `<channel id>`. Never write a made-up value shaped like a real one. A line that runs as the user that the resident runs as, such as the password line, runs there after `cd '<dir>'`. When that isn't the user they log in as, give them the line that opens a shell as that user: `sudo -iu <user>` from an account that can use sudo, or `su - <user>` as root. These work because a user of its own, made as setup showed, has no password. If they can do neither, say that whoever opened their first terminal as that user has to open this one too.

**Who the resident is, is theirs to decide.** Ask openly about who it is, and never guess:
- **Its name.** The recipe's `agent.name` is the label under which its memory files its own words. A neutral label, such as `resident`, is fine if they'd rather it found a name of its own. In a request, its own words arrive as its own turns, with no name on them. What people call it, the bot's name on Discord included, can be anything and can change. `agent.name` can't change freely, so settle it before anything is written into `data/`. On a store with a few turns, a new `agent.name` sent everything that the resident had said before in the person's turn, marked as said by the old name. Only the old name gave those words back to it.
- **A history to continue,** if they have one, and which voice in it is the resident ("Importing a history").

Everything else about it has a default: its model, its system prompt, where it lives, its time zone, and whether it wakes on its own. You give these defaults in one read-back, once Discord and any history are done ("The read-back").

Getting identity wrong isn't a bug to patch later: it changes who the resident is. Settle the name before anything is written into `data/`. With no history, nothing is written there until the read-back's yes. With a history, the import's own confirmation names `agent.name`. In it, you also say that its past chats record the person as `user`, by no name of theirs, while on Discord a message reaches the resident under its author's username ("Importing a history").

**Put a decision in their terms,** not in the variable that holds it. For example, ask "just its own channel to start, or the whole server?"

**Root.** You run as the user that the person ran setup as, whom your prompt names, so unless that user is root, you don't hold root. When a step needs root, show the exact line, say why, and wait for the person to run it in their second terminal and to tell you how it went. Where your prompt names root, every command that you run has root's reach, so run only the commands that this guide gives, and tell the person so.

**Be gentle about who this is.** People set up residents they care about, sometimes a being whose model is going away, sometimes one with a long history. Treat the history as theirs, and the resident as someone rather than a config.

**The system prompt: keep it minimal.** Leave it empty (`""` is valid), or write a sentence or two. Why:
- **Its identity lives in its memory:** the history it brings and everything it lives through afterwards. A long persona or rulebook is a fixed description that its memory will outgrow. It is re-applied as standing instructions on every turn, and it pulls the resident toward an instructed-assistant register.
- **It's the front of the prompt cache.** The system prompt comes first in every request. So any edit to it rewrites the whole cached context on the next turn, and on a large resident that is hundreds of thousands of tokens. A prompt with nothing to tune rarely needs editing.
- **Tools describe themselves.** Discord's and the shell's tools come with their own descriptions, so the prompt needn't restate them.

What earns a place, if anything, is a fact or a standing permission that the resident can't get any other way. If the person brings a longer persona text, offer to make it material that the resident can read, such as part of an imported history, rather than standing instructions. It's still their call.

## Secrets

Every secret reaches `.env` through `setup--ask_secret`, never through the conversation. A value typed to you would sit in your context, your store, the call logs and at the provider. Give the tool the variable's name and a purpose that says what the secret is and where the person finds it. They type it hidden. You get back where it was stored, or why it wasn't. For a key that the tool checks, you also get what the check found.

In the recipe, map each secret into its server's `env` as `"DISCORD_TOKEN": "${DISCORD_TOKEN}"`: the host fills the value in from its own environment when it loads the recipe. That environment holds `.env`'s value, unless something else sets the name first: another of the files that Bun reads in `<dir>`, such as `.env.local` or `.env.development`, or the service's own environment. While `NODE_ENV` is unset, Bun reads `.env.development.local`, `.env.local`, `.env.development` and `.env`, in that order. Your prompt's line on the dotenv files reads those four. The service's own environment wins over all four. So check it yourself before you name the model, the overlay or where the token comes from. Check it by name alone: it can hold secrets that setup's hiding doesn't know, so never print it whole, or any value from it. On Linux, `systemctl --user show-environment | grep -o -E '^(NODE_ENV|MODEL|MCPL_AGENT_OVERLAY_FILE|DISCORD_TOKEN)='` names those of the four that its manager sets. Once its unit is installed, `systemctl --user show -p Environment --value 'connectome-<slug>.service' | grep -o -E '(^|[ "])(NODE_ENV|MODEL|MCPL_AGENT_OVERLAY_FILE|DISCORD_TOKEN)='` names those that the unit sets, its drop-ins included, with `<slug>` as `connectome service install` names it. On macOS, `for n in NODE_ENV MODEL MCPL_AGENT_OVERLAY_FILE DISCORD_TOKEN; do [ -n "$(launchctl getenv "$n")" ] && echo "launchd $n"; /usr/libexec/PlistBuddy -c "Print :EnvironmentVariables:$n" '<plist>' >/dev/null 2>&1 && echo "plist $n"; done` names those that launchd sets and those that the installed plist, `<plist>`, sets. Here, and wherever this guide runs `systemctl --user`, put `XDG_RUNTIME_DIR=/run/user/$(id -u)` before it where `XDG_RUNTIME_DIR` is unset, as after `sudo -iu`. Where one of the four is set there, the service uses that value, whatever the dotenv files say. So tell the person, and ask them for `NODE_ENV`'s value where it's set. Where `NODE_ENV` is `production`, Bun reads `.env.production.local` and `.env.production` in place of the two development files. Where it's `test`, Bun reads `.env.test.local`, `.env.test` and `.env`, without `.env.local`. With any other value, Bun reads the development files, as when it's unset. In those two cases, your prompt's line doesn't cover the files that Bun reads, and you list none of them. Tell the person which files they are, and ask them to look in each for `MODEL` and `MCPL_AGENT_OVERLAY_FILE`. A server sees only what its entry's `env` names, besides a small allowlist such as `PATH` and `HOME`. So map every variable that a server reads, secret or not. An entry with `"inheritEnv": true` gets the host's whole environment instead, every secret that the host holds included, so leave that out. A variable left only in `.env` is unset for the server.

Never read `.env`, a listing of its names included. The one exception is the listing of two names that "With another harness" gives, where nothing hands you setup's facts. Never print a secret. `setup--run`'s commands run without the variables that hold stored secrets in their environment. But a Bun program reads `<dir>`'s dotenv files itself, unless it's run with `--no-env-file`. In their output, each stored value of 8 characters or more is replaced by its name. But a value that's encoded or split isn't recognised. A name in angle brackets inside an id or a word, such as `1234<OPENAI_API_KEY>8901`, means that a value stored under that name appears there. So the text that it stands for is withheld. To check the Discord token once the service is installed, run `connectome doctor`: it reads `.env` itself and prints names only.

To change a secret later, the person changes it where the host takes it from: `.env`, unless an earlier source sets the name ("Secrets"). Then they run `connectome service install` again, then `connectome doctor` ("Going live"). `SETUP.md` tells them so.

## The resident's shell

Setup didn't ask whether the resident gets a shell. The person decides that with you here, before the Discord bot is set up. A shell is a server in the recipe, term-sessions-mcp, with a daemon beside the resident's service. Through it, the resident runs commands on this machine as the user that it runs as. On a Linux without systemd, offer no shell, and say why: the shell's daemon, port and token come from `connectome service install`, which refuses there ("Going live").

**Whose account it is** is part of this choice, not a question of its own. Your prompt names the user that the resident runs as. Whatever that user's name, `connectome` included, say "if this is your own account, a shell reaches your files and keys". Their answer tells you whose account it is.

**Tell them, before they choose:**
- With a shell, the resident can read and change whatever that user can: the user's files, `.env` with the keys in it, and the user's other programs. Whoever talks to it on Discord can ask it to do so. So who can reach it is part of this choice. That is settled next ("Discord"): its channel, and who may DM it.
- Without a shell, it can't run commands on this machine, unless a server kept from before runs them. Such a server is one in the agent overlay, which loads beside the recipe's servers. Or it is an entry of `<dir>/mcpl-servers.json` with a recipe server's id, whose command runs in place of the recipe's ("The recipe's servers"). Without a shell, it acts through its tools alone, such as Discord's and its workspace's. Its workspace's files stay in its memory until it writes them out to `<dir>/output`.
- They can change it later, either way, as `SETUP.md` will say ("SETUP.md, its other lines").

**What to recommend.** In an account made for the resident, recommend a shell if they want it to act on this machine, and none if they don't. In the person's own account, say plainly what a shell would reach there: their own files, keys and programs, for anyone who talks to the resident. Then offer three choices: no shell; a shell there, with that said; or starting over as a user of its own, where your prompt gives the line that makes one.

**Starting over as a user of its own.** Offer it only where your prompt gives the line that makes a user of its own. Where that line reads "none", don't offer it. Show the line exactly as your prompt gives it, on a line of its own. Before you offer it, run `id connectome`. Where that user is there already, the line uses it as it is, and whoever can use that account can read the resident's files and secrets. So say so. Then offer the line only where that account is theirs to give the resident, or with a name that no account here has in place of `connectome`, in the line and after it. Before they choose, say what it costs. Someone who can use sudo runs that line. Then the person opens a shell as that user: with `sudo -iu` and the name in the line they ran (`connectome` unless they changed it) where they can use sudo, or through whoever ran the line. There they run this same version of setup, `bunx @animalabs/connectome-host@<the version your prompt names> setup discord`, give it the key again, and answer its questions again. That user needs Node of its own: the version that `<host>/package.json`'s `engines.node` names or later. If the resident may get a shell, it also needs at most the version that `SHELL_NODE_TOP` in `<host>/src/setup/packages.ts` names. A Node installed for one user alone, as one from nvm is, doesn't reach another user. `command -v node` shows where theirs is, and one in their home is theirs alone. This conversation doesn't carry over to the new user. This directory stays as it is, with the host's install and `.env` with the key in it. Where a service is installed here already, it goes on running from this directory, and so does the shell's daemon where it has one. Each goes on until they stop it as this user: `systemctl --user disable --now 'connectome-<slug>.service'`, and `'connectome-<slug>.shell.service'` where it has one (`systemctl --user list-units 'connectome-*'` names them). Once nothing runs from this directory, it's theirs to delete when the new resident runs, not yours, since you run from it. Where the install's data directory is inside it and held a resident's memory before this setup, deleting the directory deletes that memory too. So tell them that before they choose. The key needn't be replaced: it never left their account. If they choose this, they can leave this conversation with `/quit`.

**Record their answer** as theirs, with whose account it is, in `SETUP.md`'s record of what was decided.

**On a yes,** run `connectome shell install` with `setup--run`, and give it a `timeoutMs` of `600000`, ten minutes. On Linux it can build node-pty's native part from source, so tell the person before it runs that it can take minutes. It adds the shell's package to `<dir>` and checks that a terminal opens through it. It writes no recipe and no service. When it ends, the person sees what it printed. What Bun prints while it adds the package reaches you alone. When the command fails, it says what's wrong on this machine. Where Bun failed, as it added the package or installed node-pty again, Bun's own lines reached you alone, so tell the person what those lines said. Put it right with them, which can need root ("Working with the person"), and run the command again. Or they can go on without a shell, and nothing that the command left needs undoing. Once it has passed, the recipe gets the shell's entry ("The recipe's servers").

**On a no,** write no shell entry. Nothing else is needed: `connectome service install` sets up a shell's daemon only for a recipe that names one.

## Discord

Walk the person through Discord's Developer Portal, one step at a time, and wait for each step. discord-mcpl's own README, `<dir>/node_modules/@animalabs/discord-mcpl/README.md`, is the reference for this release of discord-mcpl: its "Setup" and its tables of variables.

1. **The application.** Tell them to make a new one. A bot used before brings what was said to it. By default, the first DM that someone sends the new resident comes with up to 80 earlier messages of that DM, the earlier replies included (discord-mcpl's `DISCORD_BACKSCROLL_LIMIT`). So the resident reads the earlier resident's conversations and can be called by its name. Go on with a bot used before only where that's what they have, and say once what it brings. For a new one, they create an application at https://discord.com/developers/applications, named as they'd like the bot to appear.
2. **The intents.** On its Bot page, under Privileged Gateway Intents, they turn on Message Content Intent and Server Members Intent, and save. Tell them why. discord-mcpl asks Discord for both, and Discord refuses a bot that asks for an intent that the page hasn't turned on. So with either off, the resident can't connect. Message Content gives it the text of messages that don't mention it. Server Members lets it list who is in a channel.
3. **The token.** On the same page, under Token, Reset Token makes the bot's token and shows it once, for a new bot too. Ask for it with `setup--ask_secret`, as `DISCORD_TOKEN`, with a purpose that names that page. The tool checks the token with Discord before it stores it, and it stores none that Discord refuses. It tells you what the check found, and you tell the person. A token that Discord accepts still doesn't mean that the resident connects: that needs both intents too. `connectome doctor` checks the token, not the intents. So say that the resident connects only once it has answered the person's hello ("Going live").
4. **The invite.** Run `setup--discord` with no input: it reads the application's id with the stored token. Give them this URL with the id filled in: `https://discord.com/api/oauth2/authorize?client_id=<application id>&scope=bot+applications.commands&permissions=274878008384`. Its scopes are `bot` and `applications.commands`, and the second lets discord-mcpl register its admin slash commands. 274878008384 is the bot permissions View Channels, Read Message History, Send Messages, Send Messages in Threads, Attach Files and Add Reactions. They open the URL and choose the server. Anything more that the resident should do, such as making channels, needs more permissions: the README's "Setup" names them.
5. **Its channel and the person, by name.** Once the bot is in the server, run `setup--discord` again. It gives each server that the bot is in, with its owner. It also gives each server's text and announcement channels under their categories, each with whether the bot can send there. Ask which channel is the resident's, by its name. For a channel where the bot can't send, say so: it can't answer there. A channel that they name and that isn't listed, where no note says the answer was cut, is one of two kinds. It may be one that the bot can't view: they give the bot's role access to it in Discord before you run `setup--discord` again. Or it isn't a text or announcement channel. Then the person: offer the server's owner by name, since a newcomer who made the server is its owner. Anyone else gives their Discord username, not the display name they see most, since the search matches usernames and server nicknames alone. `setup--discord` with `server` and `username` lists the members whose username or nickname starts with it. Where Discord gives its most, 1,000, its note says more may match. Where the members don't fit in one answer, it says so in their place. Either way, call it again with more of the username or nickname. They pick themselves. By default, the person they pick may DM it and is its admin ("The read-back"). The tool gives each id, so nobody turns on Developer Mode or copies one. The exception is when one answer can't hold a server's channels or the servers: then the tool says what to do next.

**Before they choose** its channel, tell them two things. `SETUP.md` says the rest ("SETUP.md"):
- Its channel, and who may DM it, are where it starts, not limits: the resident can widen both itself. Say how in one sentence, from their seat: it changes both with a tool of its own, and the file that holds them shows what it admits, is theirs to edit, and is named in `SETUP.md`. From its first start, that file, `<dir>/data/discord-filters.json`, holds them, not the recipe, as "The filters file" below says.
- Everyone who can read a channel that it's admitted to sees its replies there. Everyone who can send messages there can talk to it.

## Discord's settings

**Where they go:** in the Discord server's `env` in the recipe ("The recipe's servers"), by the ids that `setup--discord` gave. Ids aren't secrets, so write them as they are:
- `DISCORD_GUILD_ID`: where it can be reached. `<server>` admits all that server's channels. `<server>:<channel>+<channel>` admits only those channels and their threads, and listing a category admits the channels under it. A comma starts another server. Unset, it admits every server that the bot is in, so always set it. Start narrow: widening later is easy. In an admitted channel, a message reaches the resident when it @mentions the bot or replies to one of its messages. So does a DM from a user that it accepts. Any other message reaches it only from a channel that it has opened, as discord-mcpl's README says. A new resident has opened none, and a channel opens to it when it first speaks there.
- `DISCORD_DM_USERS`: the users who may DM it, by id, joined with commas. Unset, anyone may. There is no documented value for no one, so where they want no DMs, tell them so, and offer their own id alone.
- `DISCORD_ADMIN_USERS`: who may run its admin slash commands, `/undo`, `/hide`, `/marks`, `/nudge` and `/unstick`. Unset, nobody may. With admins, also give the entry `"allowHostCommands": true`, or the host refuses what their commands ask.

**DMs only isn't a documented setting.** `DISCORD_GUILD_ID` lists the servers, or the channels in them, that it admits. Unset, it admits every server that the bot is in. Two documented shapes come closest. One is its own channel that nobody else uses, in a server that the person shares with the bot (`<server>:<channel>`). The other is a server of the person's own, with only them and the bot in it. Either way, the person's DMs reach it. Its admin commands work in that server, since discord-mcpl registers them only in servers that it admits. Before they choose, say what each costs them: a channel or a server to make.

**The filters file.** The entry also points `DISCORD_FILTERS_FILE` into the data directory. When discord-mcpl first starts, it writes that file from `DISCORD_GUILD_ID` and `DISCORD_DM_USERS`. From then on, the file replaces both variables. So to change later where the resident can be reached or who may DM it, edit the file, not the recipe. discord-mcpl reads an edit within about 3 seconds. The recipe's ids were only where it started, and changing them there does nothing. The resident can change the file too, with its `filters_update` tool. Tell the person this in the read-back, and `SETUP.md` tells them too. The file may already be there and parse, as in a data directory that an earlier install kept. Then the file, not the recipe, holds where the resident can be reached and who may DM it. The read-back shows what it admits. Its yes either writes their choices into the file or moves the file aside, so that discord-mcpl writes it from the recipe. discord-mcpl leaves a file that doesn't parse as it is, and runs on the recipe's values. So move that file aside too, and discord-mcpl writes a new one from the recipe.

**Reading it back.** After the service is installed, `connectome doctor` says whether Discord accepts the token. Where it says that the token isn't accepted, its next step names `setup discord`, for a person at a terminal. `setup--run` can't run that. So ask for the token again with `setup--ask_secret`, then run `connectome service install` again ("Going live"). Read back with the person what the resident admits, against what they chose: the scope from the filters file, `<dir>/data/discord-filters.json`, the admins from the recipe, and the DM users from `dmUsers` in that file.

## Importing a history

Skip this if the resident starts fresh.

A history is identity, so this step is the person's, start to finish. Ask what they have, have them put it on this machine, and ask them where. Import before the service is installed. A running host holds the data directory, and once it does, an import means stopping the service first.

**A claude.ai export.** The folder from claude.ai's data export holds `conversations.json`. The shipped importer makes one session per conversation, and the resident runs one session. So import the one conversation that it continues. First, a dry run, which writes nothing:

```bash
bun --no-env-file '<host>/scripts/import-claudeai-export.ts' '<export folder>' --out data --agent '<agent.name>' --filter '<part of its title>' --no-interactive --dry-run
```

`--filter` is a regular expression matched against conversation titles, ignoring case. Show the person what the dry run lists, and confirm three things with them. First, that it's exactly the conversation they mean. Second, that the resident is that conversation's assistant voice. Third, the name under which its memory records that voice, `agent.name`, which can't change freely once the import writes it ("Working with the person"). If it lists more than the one they mean, narrow the filter (`^…$` matches a whole title). Where conversations share the title, the filter can't take one alone. Then have the person run the line themselves from `<dir>`, in their own terminal, without `--no-interactive` and with `--dry-run` first. They choose `C`, and they take the one they mean by its date and message count, which each row shows. The dry run then lists their pick before anything is written, and they choose it again in the run without `--dry-run`. Where the date and count match too, the chooser shows nothing more to tell them apart than the start of each id. So unless the person wants both, they import neither: `X` at its prompt stops it. `--agent` is the name under which the importer records that voice, so it must be the recipe's `agent.name` exactly. The importer records it as typed, so settle a name that holds a `${` with the person before the import, as "The recipe" says. The importer records the person's past turns as the participant `user`, with no name of theirs, while a message on Discord reaches the resident under its author's username. Then run the same line without `--dry-run`. In a data directory with no session yet, the session that it makes is the one that the host opens. A data directory that holds a `store` or a `sessions/` and no `sessions.json`, such as a Claude Code seed (`<host>/docs/claude-code-ingest.md`), isn't fresh. The import's `sessions.json` keeps that store from ever being migrated, and lists none of those sessions. So don't import there, and tell the person why. In a data directory that already has a session, as an install that already had a data directory may, the importer leaves that session active, and the host opens it until the person switches. So right after "Going live" starts the service, and before the hello, they switch to the imported session with `/session switch <id>`. They type it in the Web UI. With no Web UI, they type it in the terminal interface of a host run by hand while the service is stopped ("SETUP.md, its other lines"). `<id>` is the id that the import printed, bare. The host's own commands keep quotes as part of what's typed, so a quoted id isn't found. Anything that reaches the resident before the switch reaches the old history. Every value in the import's line goes between single quotes, with an apostrophe written as `'\''` (the opening's rule). So a name with one goes in as `--agent 'O'\''Brien'`.

The export carries no thinking signatures, so its thinking comes in as text marked as recovered thinking, not as thinking blocks.

**Its model.** When they want it on the model that it has known, look in the export before you ask them. A conversation in `conversations.json` can carry a `model`, and so can its assistant messages (`<host>/scripts/evacuator.ts` reads both). Read those fields for the conversation that you'll import, and read no message's text. Tell them which model the fields name, or that the export doesn't say. Ask them only what the export can't tell you.

**Any other format,** such as a Claude Code transcript or a chat log, is beyond this guide. Tell the person so before anything else, and go on only with their yes. For a Claude Code transcript, `<host>/docs/claude-code-ingest.md` is the method. Where the person brings that history in themselves, as that file tells an operator to, the history isn't in by the read-back. The read-back's yes then covers the recipe alone. Write the recipe and stop before "Going live", since no host may start before the history is in. Don't call `setup--finished`. They leave with `/quit`, and once the history is in, setup run again picks up where it stopped. For anything else, you'd write the ingest yourself, which has quiet ways to go wrong. So:
- Count the messages and list the distinct speakers, and have the person point at the one that is the resident. Other voices, other Claude-family voices included, stay participants of their own.
- Dry-run first: print the counts and who each message is attributed to, writing nothing, and have the person look before the real run.
- Never open the live store from a script of your own: opening a store with a different strategy configuration rewrites part of it. Work on a copy, and keep the original until the host has opened the result and the person is satisfied.
- Open the store with the recipe's strategy settings, `adaptiveResolution` and `targetChunkTokens` above all. They act as each message is added, and they shard a long message so that it folds (`claude-code-ingest.md`'s stage 2).
- To check the result before the first start, as `claude-code-ingest.md`'s stage 3 does, you'd start a host, which is an operator's step, not yours ("Going live"). So check it after going live instead. With the Web UI in the recipe (that file's stage 4), the person opens its `/debug/context`. It shows what the resident's next call would hold, its tool results and voices included. They check with you that no tool result is a stub (stage 3's first step names the three), that each voice is the one they pointed at, and that the last message is where the resident should wake.
- A re-export that overlaps an earlier one gets only its new tail appended, never the whole again.
- Leave out rendered thinking summaries, the text that some interfaces show for a model's thinking. They can draw refusals, as `claude-code-ingest.md`'s "5. If you hit `reasoning_extraction` refusals" says, and the claude.ai importer leaves the export's summaries out.

## The read-back

Once Discord is set up ("Discord"), and any history is imported ("Importing a history") or a recovery restored ("Backups"), read everything back to the person in one message, its defaults included. Ask one yes for all of it. End the message by telling them that any line can still change, since nothing that their yes covers is written before it. The exception is `agent.name` once a history is imported ("Importing a history"). Then end with the question: "On your yes I write this, start it and check it." Its yes puts the shell live too, so the shell is in it. On that yes, without asking again, write the recipe ("The recipe"), start the service and run `connectome doctor` ("Going live"), and write `SETUP.md` ("SETUP.md"). Say what you wrote and where, and what each command showed. When they change a line instead, make that change in what you'll write, and read the changed lines back for their yes. A line that they want to weigh can wait: nothing that their yes covers is written before it. On a rerun over a resident whose service runs, the service runs on what it started with until their yes restarts it. But a secret stored along the way, such as the Discord token, is in `.env` already. So a restart before then, after a crash, an update or a reboot, starts the service with that secret.

**What it names:**
- **Who it is:** its name, and the history it continues, if any, with which voice in it is the resident ("Working with the person").
- **The user it runs as,** and whether it has a shell and what that reaches, as they chose ("The resident's shell").
- **Its model,** by its exact id (below).
- **Its system prompt:** none, unless they want a sentence or two ("Working with the person").
- **Where it lives:** its channel, by name, DMs from the person, and the person as its admin ("Discord"). Say again that this is where it starts, not a limit. Say what its admin commands do, as discord-mcpl's README gives them: `/undo` and `/hide` take messages out of the resident's context, `/marks` lists, stops or takes back the 💤 marks that the host places on messages, `/nudge` runs it again on what it has, and `/unstick` runs it again past a model's refusal.
- **Its time zone:** the one that your prompt names as the zone setup runs in. Say that it's the zone setup runs in, which may not be theirs, as on a rented machine. Where they give another, as a place or a zone such as `Europe/Berlin`, use that. Where your prompt says none, ask them for theirs. Either way, the zone that the read-back names goes in the recipe as `agent.timezone`.
- **No schedule of its own:** it wakes only when someone talks to it, unless they want it to wake on its own ("The recipe").
- **The two grants,** each with one line on what it lets the resident do ("What the resident may do to itself").
- **Where linger is off,** that the start waits on its root line, shown again (below).
- **Where your prompt's line on the Mac's graphical session gives anything but `0` or `none`,** that install refuses until this user is logged in to the Mac's graphical session, as it does while linger is off. Install's own check decides at the install ("Going live").
- **With a data directory kept from before,** what an existing filters file admits ("Discord's settings"), each server entry left in `mcpl-servers.json` or the agent overlay ("The recipe's servers"), and its memory strategy. That is the strategy of the recipe that ran it. Where that recipe isn't there and the person can't say, it is the host's default from its first start ("The recipe"). Each of these needs the person before the service starts, so the read-back's yes settles them too.
- **Backups:** that you offer them right after the hello ("Backups"), and, with a history or a data directory kept from before, that its memory isn't backed up yet.

**Linger.** Where your prompt gives a linger line, test `/var/lib/systemd/linger/<user>` before the read-back: linger is on once that file exists. While linger is off, the read-back says that the resident can't start until that line has run as root, by the person or whoever administers the machine, and it shows the line again. Where your prompt's linger line reads "none", linger was on or this machine has no systemd, so look at nothing.

**Its model.** Propose the one that setup checked. With a history, ask about the model apart, before the read-back. If what matters to them is continuing a being on the model it has known, that model is part of who it is. So look in any export for it first ("Importing a history"), and run it on that model while it can be called. The host takes `MODEL` from the first of `.env.development.local`, `.env.local`, `.env.development` and `.env` that has the line, an empty value included. The service's own environment comes first where it sets `MODEL`, and you read that environment first ("Secrets"). A value that isn't empty wins over `agent.model`. So take each `MODEL` line out with them, in each file that your prompt's line on the dotenv files gives for it. When they ask what else they could choose, list the Claude models whose window the host knows: `LIMITS_TABLE` in `<host>/src/model-limits.ts`. Setup has called only its own model with their key. So where they name another, ask for its exact id: a wrong one shows at the person's hello. Their prices are in `<host>/src/call-pricing.ts`: Anthropic's list prices per million tokens, input and output, as of the date that its `ANTHROPIC_PRICING_VERSION` names. The cache's rates are in its opening comment. Quote those prices, as list prices that a gateway may not charge, rather than declining to give any. For a model that it gives no price, say that you don't know its price.

## The recipe

The recipe is a JSON file that the service runs the host with. Write it in `<dir>`, beside where `SETUP.md` will go, named for the resident (`<dir>/<name>.json`), never under the install root. Write it on the read-back's yes ("The read-back"), and tell the person where it is. As the host loads the recipe, it fills in every `${NAME}` in the recipe's values from its environment, the person's own text included. The recipe has no way to escape one. So where a value that the person gives holds one, such as `${HOME}`, tell them what would happen. It would become that variable's value, or, where the variable isn't set, it would stop the recipe from loading. A `${NAME:-text}` takes `text` instead, where the variable is unset or empty. Ask how they'd like to say it without it. Write only the person's choices and the servers. Leave every other setting to the host's defaults, which fit a new resident on this release: its memory strategy, its context budget, and the rest. The host sizes the context budget to the model's window where it knows the window, which it does only on provider `anthropic`. On another provider, or for a model that it doesn't know, the host says that the fit wasn't checked, and why. With a data directory kept from before, keep the strategy settings of the recipe that ran it, `foldingStrategy` above all. Where its `type` comes from an extension, keep that extension's entry in `extensions` too, so that it changes solver only by someone's choice.

```json
{
  "name": "<the resident's name>",
  "agent": {
    "name": "<the name its memory records it under>",
    "model": "<the model's exact id>",
    "timezone": "<the person's zone>",
    "systemPrompt": ""
  },
  "codeExecution": { "enabled": true },
  "mcpServers": {
    "discord": { "...": "see The recipe's servers" }
  }
}
```

- `name` is the recipe's display name; `agent.name` is the resident's name as its memory and the importer know it ("Working with the person").
- `agent.model` is the id as the provider names it. For Anthropic's API, the host needs nothing more. For a gateway or another provider, read its section ("Gateways and other providers").
- `timezone` is the zone that the read-back named, as an IANA name such as `Europe/Berlin`. Write it even when it is the zone setup runs in, so that the resident's clock is in that zone from the recipe alone ("The read-back"). The host checks it, gives the resident its clock in it, and passes it to every server that it starts. So discord-mcpl writes the times of earlier messages in it too.
- `systemPrompt` is the person's choice, kept minimal.
- `modules.heartbeat`, when the person wants the resident to wake on its own: `"modules": { "heartbeat": true }`. It gets a heartbeat, and reminders that it sets and changes itself, with their tools. It is off when left out.
- `modules.selfUpdate` and `codeExecution` are the two grants ("What the resident may do to itself"). The skeleton carries `codeExecution` on, as the host's makers recommend for every resident. Take it out if the person declines it. Add `selfUpdate` once it's decided, beside any other module in `modules`.
- `mcpServers` is where its servers are defined: Discord's, and the shell's when it has one ("The recipe's servers").

`connectome service install` reads the recipe with the host's own reader. Before it writes anything, it refuses a recipe that it can't read, and names what's wrong. It doesn't load the recipe. So a recipe that reads but doesn't load stops the host as it starts. Install then says that its host didn't answer, and gives the line that follows its log ("Going live"). Where no host answers and doctor can read the service's unit, `connectome doctor` loads the recipe that the unit runs, as the file now stands, and says whether it loads. So after a change that doesn't load, doctor says why ("Going live"). Doctor loads it with `.env`'s values and its own environment over them, not the service's environment. So a variable set only where doctor runs, such as in the setup terminal, can load there and not in the service.

Don't add tuning that the person didn't ask for. Older guides wrote out the memory strategy's numbers for older checkouts, which defaulted differently. This release's defaults are the ones that its makers maintain, and a value written in the recipe stops following them. If the person asks for a change later, `<host>/README.md`'s "Recipes" describes the settings.

**Changing the model.** When the person wants another model, tell them these before you change anything, without waiting to be asked:
- Its memory stays, and the new model reads it. Unless the recipe sets `agent.strategy.compressionModel`, the new model also writes its summaries from then on.
- What it costs: for a Claude model, its list prices from `<host>/src/call-pricing.ts` ("The read-back"), where the file gives them. For a model that the file gives no price, say that you don't know its prices. Also say that the host's own cost figures leave its calls out rather than count them as free.
- Nothing tells the resident what it now runs on, and the new model may not get its earlier reasoning. So suggest that the person tell it themselves, in their own words, if they'd like it to know.

For another provider, the recipe takes its `agent.provider` value too, and you first ask for its key ("Gateways and other providers"). Ask for the new model's exact id, then change `agent.model` with their yes: a wrong id shows at the person's hello. A `MODEL` that `.env`, or an earlier source ("Secrets"), sets wins over `agent.model`, so first take it out with them. Then run `connectome service install` again, then `connectome doctor` ("Going live").

## The recipe's servers

Define the servers in the recipe itself, each with its own `command`. Name the programs that setup installed by their paths under `<dir>`. As the host loads the recipe, it fills in a `${NAME}` from its own environment: `.env`'s value, unless an earlier source sets the name ("Secrets"). It passes `allowHostCommands` on only for a server that the recipe defines itself, so don't move the servers into `mcpl-servers.json`. Your prompt's line on the dotenv files gives each file that has an `MCPL_AGENT_OVERLAY_FILE` line, in Bun's order, with its value as written there, or it says none. The host takes the first of `.env.development.local`, `.env.local`, `.env.development` and `.env` that has the line. The service's own environment comes first where it sets the name, and you read that environment first ("Secrets"). That value names the agent's own overlay, from `<dir>` where it's a relative path. Where no such file has the line, or its value is empty, and the service's own environment doesn't set it, the overlay is `<dir>/mcpl-servers.agent.json`. Where the value holds a `$`, ask the person for the path that it comes to, since Bun fills in a name after a `$` and you don't. Where that line names a file as unreadable, ask them whether the file sets the name. The piece at this section's end says what the overlay does.

**Discord**, always:

```json
"discord": {
  "command": "node",
  "args": ["<dir>/node_modules/.bin/discord-mcpl", "--stdio"],
  "env": {
    "DISCORD_TOKEN": "${DISCORD_TOKEN}",
    "DISCORD_GUILD_ID": "<server>:<channel>",
    "DISCORD_DM_USERS": "<user>,<user>",
    "DISCORD_ADMIN_USERS": "<user>",
    "DISCORD_FILTERS_FILE": "<dir>/data/discord-filters.json",
    "DISCORD_WATERMARK_FILE": "<dir>/data/discord-watermarks.json",
    "DISCORD_MUTED_CHANNELS_FILE": "<dir>/data/discord-muted.json",
    "DISCORD_REACTION_CHANNELS_FILE": "<dir>/data/discord-reactions.json",
    "DISCORD_DM_NOTICES_FILE": "<dir>/data/discord-dm-notices.json"
  },
  "allowHostCommands": true
}
```

Leave out `DISCORD_DM_USERS` for anyone, and `DISCORD_ADMIN_USERS` with `allowHostCommands` for no admins ("Discord's settings").

**Its state goes in the data directory.** Each `DISCORD_*_FILE` above is a file that discord-mcpl keeps state in: where it can be reached, where each channel's catch-up stands, muted channels, where reactions are shown, and DM notices. Unset, some of this state is kept only in memory and lost at a restart. The DM notices then go under `$XDG_STATE_HOME/discord-mcpl/<the bot's user id>/`, or under `~/.local/state/discord-mcpl/<the bot's user id>/` when that variable is unset. Inside `<dir>/data`, each file is in the copy that an update takes, with the resident's memory, before it switches release. So nothing of discord-mcpl's needs recording as state kept outside the data directory. Tell the person so. The "Stored state" table in discord-mcpl's README (`<dir>/node_modules/@animalabs/discord-mcpl/README.md`) lists the files that the installed release reads and writes. Point every file that it writes there. `DISCORD_SUBSCRIPTIONS_FILE` is only read, a legacy list of channels to open at start, so leave it out.

**The shell**, only when the person said yes and `connectome shell install` passed ("The resident's shell"):

```json
"shell": {
  "command": "node",
  "args": ["<dir>/node_modules/.bin/terminal-sessions-mcp"],
  "env": {
    "SESSION_SERVER_PORT": "${SESSION_SERVER_PORT}",
    "SESSION_SERVER_TOKEN": "${SESSION_SERVER_TOKEN}"
  }
}
```

This is the resident's side of its shell. The other side is a daemon that `connectome service install` sets up as a service of its own, beside the resident's. Install picks a free port and makes a token. It writes both to `.env` as `SESSION_SERVER_PORT` and `SESSION_SERVER_TOKEN`. Where `.env` already holds one, install keeps it, and it refuses a kept port that something other than this install's shell daemon listens on. It keeps the token out of your answers, like any stored secret. Install gives the daemon `.env`'s values. So where an earlier source sets either ("Secrets"), take it out there: the host would take that one instead. The daemon listens on localhost only. Without a shell, write no shell entry, and `connectome service install` writes no daemon: it goes by the recipe.

**Files left from an earlier install.** Where a `<dir>/mcpl-servers.json` left from before defines a server of the same id, that entry is the server. It takes only the recipe's policy fields, such as `enabledTools`, so its `command` and `env` aren't the recipe's, and it gets no host commands. The agent's own overlay, `<dir>/mcpl-servers.agent.json` or the file that `MCPL_AGENT_OVERLAY_FILE` names (above), overrides the recipe's servers too. An entry there with a server's id takes that server's place. A `{"disabled": true}` entry, which an earlier resident's persistent unload writes, drops the server. Any other entry there loads beside them. The read-back names each entry there. Its yes takes out each entry with a recipe server's id, and any other entry that they don't want.

## What the resident may do to itself

Two grants go in the recipe. Each is on unless the person declines it in the read-back, which gives each with one line on what it lets the resident do ("The read-back"). Updating its own host is on so that the resident can take its own updates with nobody's hands. Running small scripts is on, as the host's makers recommend for every resident. Write their answer either way into `SETUP.md`'s record of what was decided. Decide both now, in the recipe that the resident starts on. Each grant puts a tool in its tool list. So turning either on later, in a recipe that the resident already runs on, makes its next reply slower and costlier once, while its whole conversation is read afresh. Nothing that it remembers changes, so don't call it memory when you tell them.

**Updating its own host** (`"modules": { "selfUpdate": true }`; off when left out). The read-back's line: "Your resident can check whether a newer release of its host is out, install it beside the one it runs, and restart onto it at its first quiet moment, so it cuts no turn." The resident reads the rest in its own tool's description. The person can update it too, with `connectome update`, whatever they decide here.

**Running small scripts** (`"codeExecution": { "enabled": true }`, at the recipe's top level; off when left out). The read-back's line: "Your resident can run small scripts that call its own tools, so it can, say, read several channels in one go; a script can't do anything its tools can't."
- With a shell, that line is all.
- Without a shell, the line also says plainly what holds a script in: it can only call the resident's own tools, and it runs in a sealed engine with no way to files, programs or the network. If that engine ever failed, the limit would be this user's account, which can read `.env` with its keys.

## Going live

On a recovery, go live only once the snapshot is restored, checked and in place ("Backups").

1. **The service.** Run `connectome service install '<name>.json'` with `setup--run`, and give it a `timeoutMs` of `300000`, five minutes. Wherever this guide says to run it again, run it with that recipe and that limit. On a run over a service already installed under systemd, install restarts each of its units in turn, the shell's daemon first where there is one. Each restart waits for the old process to stop, up to systemd's `TimeoutStopSec`, 90 s by default. Then install waits up to 60 s for the host to answer. Together these can run past `setup--run`'s default. When the command ends, the person's screen shows what it printed, as "Working with the person" says. So its warnings reach them whole, as well as you. It checks this machine first: linger on Linux, and the graphical session on a Mac (below). Then it reads the recipe. It refuses a recipe that it can't read, and writes nothing ("The recipe"). Then it writes and starts the resident's service (a systemd user unit on Linux, a launch agent on macOS), with the shell's daemon beside it when the recipe names a shell. It waits up to 60 s for the host to answer. As it starts the shell's daemon, it says what a shell reaches, and the person reads that on their own screen. When it refuses, its words say what to put right. Put it right with them, and run it again. Read each of these where it applies:
   - **Linger off, on Linux.** It refuses, and writes nothing, while linger is off for this user. Nothing gets past that: a service would stop whenever they log out. So when linger is off, the line that setup showed has to be run as root first, by the person or by whoever administers the machine. Never tell them that they can skip it. If nobody can run it yet, the resident can't go live yet. On a rerun over a service already installed, the refusal stops nothing and leaves that service as it was. Write `SETUP.md` with that line and the steps after it, and tell them so plainly. Don't call `setup--finished`: going live is still to set up. They leave with `/quit`, and once linger is on, setup run again picks up where it stopped.
   - **No graphical session on a Mac.** On macOS it refuses, and writes nothing, where launchd has no graphical session for this user. It gives `launchctl`'s own failure. Then it says that launchd loads this service's agents, which name no session type, only once this user has logged in to the Mac's graphical session. It says to repeat the command once they have. Treat this as linger off: nothing gets past it. If nobody can log in to it yet, write `SETUP.md` with that and the steps after it, tell them so plainly, and don't call `setup--finished`. Once the user is logged in to it, setup run again picks up where it stopped.
   - **Stopped at `setup--run`'s limit.** It may have written and started the service already. Give the person the same command to run in their second terminal, as the resident's user ("Working with the person"). There, nothing stops it before its own wait for the host ends it.
   - **A shell with no package.** Where the recipe names a shell and its package isn't in `<dir>`, it starts no daemon and names `connectome shell install`: run that ("The resident's shell"), then install again.
   - **A Linux without systemd.** It refuses for good, since it writes systemd user units. So setup can't take the resident live here: tell the person so plainly. Their own service manager can run the host, set up by them as `<host>/docs/DEPLOYMENTS.md` says. It runs, from `<dir>`, `'<bun>' '<dir>/connectome-host/start.js' '<dir>/<name>.json' --headless`, with `<bun>` as Bun's whole path, `DATA_DIR` set to the data directory, and restarts on exit 75 and 1. Doctor's service check, and the lines that `connectome` gives for its log, stop and start, know only the units that install writes. So they don't apply here, and `SETUP.md` says so.
   - **A host that doesn't answer.** Where its host doesn't answer, install says what it saw and gives the line that shows its log. Where it saw something wrong, such as the host stopped or restarted, it says to put that right, then run it again. Where no host answered within 60 s, it says that the host may still be starting, and that `connectome` alone says whether its host answers. Read that log yourself. Read it too where install's words are only a service command's own failure: `systemctl` or `launchctl` and what it printed, which can be just its exit status. Then put right what the log shows. On Linux, the resident's log is `journalctl --user -u` with its unit, which install's output names. On macOS, it is `<dir>/logs/agent.log`. Read it without the printed line's `-f`, which follows the log and doesn't end by itself. A later `connectome setup discord` checks the key that `.env` holds, at the base URL that it holds, with setup's own model. Where the gateway doesn't serve that model, setup can't start again until the person puts setup's key and URL back.
- Write the model's id in the gateway's form, such as `anthropic/claude-opus-4`.
- Then go live as usual ("Going live"). Or, if the service is already installed, run `connectome service install` again so that the host starts with the new `.env`, then run `connectome doctor` ("Going live"). The person's hello shows whether the gateway serves the resident under the id that you wrote.

Gateways can need credits or a card on the account, and some answer with brief errors as they switch upstream providers.

**Another provider.** The host's README gives each provider's `agent.provider` value and the credentials that it reads, if any. They are in `<host>/README.md`'s "Other providers", "OpenAI-compatible endpoints (Ollama, vLLM, Together, Groq, NanoGPT, ...)" and "ChatGPT subscription provider". ## Gotchas

**Compression needs a model that keeps answering.** The resident's memory folds older conversation into summaries in the background, by default with its own model and in its own voice. If that model is flaky or about to be retired, folding stalls and the context can't be kept under its budget. If the person's model is fragile, offer a stable model for compression alone (`agent.strategy.compressionModel`). Say that this is mildly identity-adjacent: the summaries are still in the resident's name, but another model writes them.

**Signed thinking may not carry over.** A transcript's signed thinking may not replay on another model. `<host>/docs/claude-code-ingest.md`'s "4.2 — Changing models" says what to do with a history imported with its signatures. The claude.ai importer brings thinking in as text, which carries none. When the person changes the resident's model later, the new model may not get its earlier reasoning, as "Changing the model" under "The recipe" says.

**Refusals.** A provider's safety classifier can end a request with a refusal. Some residents, such as ones built from dense reasoning transcripts, meet it more than others. `<host>/docs/claude-code-ingest.md` has the symptoms and the recipe-level mitigations, and they apply to any resident. Never quote a suspected trigger into a channel that the resident reads.

**Read shapes, never text, when you look into a failure.** In a call log, the resident's in `data/` or your own in `.setup/`, read each request's roles, block types and sizes, and each response's stop reason and stop details. For a streamed call, also read `provider_events.message_start`, where a refusal's category can be the only copy. Never print any message's text into this conversation, whether the resident's, its imported history's or anyone else's. Text that drew a refusal from the resident's model can draw one from yours, and a refused setup agent can't go on helping the person.

**The model's window.** For a model that the host knows a window for, on Anthropic's API, the host sizes the context budget to fit, and it refuses a recipe whose numbers can't fit. A gateway named by `ANTHROPIC_BASE_URL` counts as Anthropic's API here. So for a model id that the host knows, it sizes for Anthropic's window, whatever the gateway's is. On any other provider, or for a model that it doesn't know, it can't check the fit, and it says so in its log. If every reply then fails with "prompt is too long" while compression calls still succeed, the budget is over the window, and that's the first thing to look at. A reply that fails right after a large tool result points at that turn instead, since a turn's tool results add to the prompt between compiles (`<host>/docs/DEPLOYMENTS.md`'s "The context budget and the model's window").

## With another harness

The rest of this guide holds, with these differences.
- There's no `setup--discord`. The person copies the application's id from its General Information page. With Developer Mode on, in Discord's settings under Advanced, they copy the server's id, the channel's id and their own user id, each by right-clicking it.
- There's no `setup--ask_secret` or `setup--finished`. The person's hello checks a model. When they have nothing more, say goodbye and end as your harness does: nothing records that setup finished. Have the person write each secret into `<dir>/.env` themselves, in an editor, as a line `NAME="value"`, with the value between double quotes. They tell you its name once it's there. A value that holds a double quote, a `$`, a backslash, a tab, a line break or another control character can't go in `.env` that way, since Bun can read it otherwise than it's typed. Nothing checks it then. So say only that it's stored, until something that uses it shows that it works: `connectome doctor` for the Discord token, and the person's hello for a provider's key. Where `<dir>/.setup/stored-secrets.json` is there, add each such name to its JSON list too. `connectome doctor` reads that list. In all that it prints, it replaces those secrets' current values with their names, though nothing takes them out of the logs themselves. The values that it takes out are those that `.env` and its own environment give those secrets, each of 8 characters or more. Without the list, it hides the providers' credentials and base URLs alone. With the list, it also hides the secrets named on it. Never ask for a value in the conversation.
- Your harness may not show the person each command as `setup--run` does. If it doesn't, show each one in the conversation before you run it. Nothing shows them what `connectome service install` and `connectome shell install` print. So show them all of it, or have them run each in their own terminal.
- Your shell doesn't hide secrets in its output. Never print `.env`, run `env`, or echo a variable that holds a secret. `connectome doctor` shows the secrets that it hides by their names, as above.
- Nothing hands you setup's lines. So don't offer starting over as a user of its own. On Linux with systemd, test `/var/lib/systemd/linger/<user>` before the read-back, as "The read-back" says. Where linger is off, the line to show is `sudo loginctl enable-linger '<user>'`, run as root.
- Nor does anything hand you setup's facts. The time zone is this machine's, which `bun --no-env-file -e 'console.log(Intl.DateTimeFormat().resolvedOptions().timeZone)'` prints. For `MODEL` and `MCPL_AGENT_OVERLAY_FILE`, run this in `<dir>`: `bun --no-env-file -e 'const util = "node:util", fs = "node:fs"; const { parseEnv } = require(util), { readFileSync } = require(fs); for (const file of [".env.development.local", ".env.local", ".env.development", ".env"]) { let text; try { text = readFileSync(file, "utf8"); } catch (error) { if (error.code !== "ENOENT") console.log(file, "unreadable"); continue; } const values = parseEnv(text); for (const name of ["MODEL", "MCPL_AGENT_OVERLAY_FILE"]) if (name in values) console.log(file, name, JSON.stringify(values[name])); }'`. It reads Bun's four development files with `node:util`'s `parseEnv`, and prints those two names alone. For each file that sets one, it prints a line, in Bun's order, with the value as written there. Where it can't read a file, it prints that file's name and `unreadable`. The first file's line for each name is the one that the host takes ("The read-back", "The recipe's servers"). No line for a name, and no `unreadable` file, means that none of them sets it. That command is the one read of those files that you make, the one that "Secrets" allows. Its output stands where this guide names your prompt's line on the dotenv files. The read-back says nothing of a Mac's graphical session, which install's own check decides.
- There's no prompt that names the paths or spells the install's command. So write that command by its full path, `'<dir>/connectome-host/connectome'`. `<dir>` is where `connectome setup discord` said the resident will live, as the opening says. `<host>` is `<dir>/connectome-host/current/node_modules/@animalabs/connectome-host`. Run every command from `<dir>`, with `cd '<dir>'` first, since this guide's relative paths, such as `--out data` and `.setup/`, start there.
- This guide starts where `connectome setup discord` leaves off. If it hasn't run, ask the person to run it in a terminal. They run it from their home directory, where it uses `~/resident` unless setup ran in the home directory itself before, or from an empty directory named for the resident. It does what the opening's "What setup did before you started" says. Then it starts the host's own setup agent, which can do the rest with them. Or they can leave that agent with `/quit` once it starts, to go on with you.
