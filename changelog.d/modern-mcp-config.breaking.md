- **`mcpl-servers.json` entries** now pass their `url`, `transport`, `token`, `access`, `protocol` and `requestTimeoutMs` to agent-framework, and are checked by the framework's rules. The loader used to drop all six, so an entry with a `command` always ran it, and one without could never connect. Now an entry without a `command` dials its `url`, and one without a `command` that agent-framework can't use (no `url`, one that isn't `ws`, `wss`, `http` or `https`, or a `transport` the `url` contradicts) stops startup even when the recipe doesn't use it, as an invalid `inheritEnv` or `toolLifecycle` already does. None of those could connect before.
- **A `transport`**, wherever a server is defined. agent-framework 0.21 honored only `"stdio"` and `"websocket"`, and otherwise chose by `command` and `url`. `mcpl-servers.json` lost the field entirely. Now:
  - `"http"` with an `http://` or `https://` `url` dials the url as a modern MCP server. This includes an entry that also has a `command`, which used to run it.
  - In `mcpl-servers.json`, `"websocket"` with a `ws://` or `wss://` `url` dials the url, also where a `command` is given, which used to run. A recipe or overlay entry already dialed it.
  - Anything else stops startup in a recipe or `mcpl-servers.json`, and skips an overlay entry: `"websocket"` or `"http"` with no `url` or with a `url` of the other kind, and any value but `"stdio"`, `"websocket"` or `"http"`, such as `"ws"` or `"WebSocket"`. Many of these connected before: `{ "url": "wss://…", "transport": "ws" }` dialed, and `{ "command": "…", "transport": "http" }` ran. Drop the `transport`, or write `"websocket"` for a `ws(s)://` url.
- **`requestTimeoutMs`** now applies in two places that dropped it, `0` included: a `mcpl-servers.json` entry, which got the 60-second default, and a recipe entry that names a `mcpl-servers.json` server by id, which validation accepted and the merge then dropped.
  - **Its rule:** a number from 0 to 2147483647 (about 24.8 days), wherever it is set. A larger value now fails recipe validation, where it used to pass: a legacy server's timer can't hold it, so its calls timed out at once.
  - **A value the rule refuses** (a negative number, a string, `null`, or one too large) stops startup in `mcpl-servers.json`, as it does in a recipe, and skips an overlay entry. A legacy server given a negative number or a non-numeric string would run without a timeout.
- **An agent's overlay entry** that the host or agent-framework would refuse is skipped at startup, and an operator's server with its id runs instead. The host's log and `mcpl_list` give the reasons. Before, every entry with a `command` or `url` replaced the operator's server, whether or not it could connect.
  - **Earlier deploys of an `http(s)://` url:** `mcpl_deploy` used to write `"transport": "websocket"` with every url, so an agent that deployed one holds `{ "url": "https://…", "transport": "websocket" }`. That entry never connected, and is now skipped. Deploying the url again writes a modern server.
  - **Today's `mcpl_deploy`** refuses an entry the boot would skip, before saving it.
- **Unchanged:** an entry with `command` and `url` and no `transport` still runs its command, wherever it is defined.
