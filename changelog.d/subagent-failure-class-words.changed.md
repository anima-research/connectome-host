- A subagent's failure that isn't the host's own reaches its parent in fixed words, where the parent read the error's message. That holds for the synchronous tool result and the asynchronous "[Subagent '<name>' failed]" notice alike. An agent-framework error's message can carry a provider's words, and the host can't tell them from any other, so a parent no longer reads an error's own wording, the framework's included. The words take one of these forms:
  - Where the error's cause is membrane's, with a type from membrane's own set that decides its class, its type and HTTP status in agent-framework's companion change's form for a membrane error, such as "the model call failed (invalid_request, HTTP 404)". For `unknown`, and `server` with no status, the class words below apply, since the host classes those by their words.
  - Otherwise the class the host's classifiers give it: a stated wait the run won't sleep, with the wait, such as "the provider asked to wait 1200 s, which a subagent's run doesn't sleep"; a rate limit, "the model call failed (rate_limit)"; a transient failure, "the model call failed (timeout, network or server)"; anything else, "the turn failed", or "it couldn't be set up" for a run that didn't start.
- The host's own failures, such as a time limit or no concurrency slot, keep their words and remedies. The message goes to the operator's log first, as `[subagent] <name> stopped: <message>`, or `[subagent] <name> didn't start: <message>` for a run that didn't start, and stays the subagent's status message.
