- `connectome service install <recipe>` writes and starts this install's resident service, and waits for its host to answer. Linux gets `~/.config/systemd/user/connectome-<name>.service`; macOS gets `~/Library/LaunchAgents/com.animalabs.connectome.<name>.plist`. The name comes from the working directory that holds `.env`. The service runs `start.js` there with the recipe, the data directory from `install.json` as `DATA_DIR`, and a PATH of Bun's directory, then Node's where `node` is found, then the absolute entries of the PATH install runs with, then `/usr/local/bin`, `/usr/bin`, `/bin`, `/usr/sbin` and `/sbin`. `connectome` shows the service manager's own lines that follow its log, stop it and start it, where the host's unit file names this directory as its working directory or can't be read. Otherwise, where a unit file of its name names another working directory, or none, it says so and gives no command; where none does, it gives the command that sets one up, if the directory's name can name a service. Run by setup's agent, `service install` also writes each line it prints to the file `CONNECTOME_SETUP_SHOWN` names, so the person sees them once it ends.
- A recipe whose text names `SESSION_SERVER_TOKEN` or `SESSION_SERVER_PORT`, or one of whose servers' command or arguments names the shell client, gets a localhost shell daemon when `term-sessions-mcp` is installed. Install keeps or writes `SESSION_SERVER_PORT` and `SESSION_SERVER_TOKEN` in `.env`, picking a free port from 3100 when needed. The token stays off the daemon's command line, and a `.env` holding it is made readable by its user alone. A shell client named only through an environment reference, such as `${CLIENT_COMMAND}`, isn't seen, so that recipe gets no daemon. Once the shell daemon starts, install says that with a shell the resident can read and change whatever its user can, and whoever talks to it on Discord can ask it to. A recipe that names a shell without `term-sessions-mcp` installed gets no daemon, and install names `connectome shell install` and the run to repeat. Once its host answers, an install with no shell daemon stops and removes this install's shell unit, and the shell's settings stay in `.env`.
- Install refuses before it writes anything in cases such as these: on a platform other than Linux and macOS; on Linux without systemd or with linger off; when run inside its own service; when run as root, as under sudo, in a directory another account owns; for a recipe the host's reader can't parse; for a unit of this install's name that runs another directory; on Linux, for another unit already set up to run from this directory, running or stopped; and when a host that isn't this unit's already answers on the data directory's socket, which it names by pid. Its host unit gets `CONNECTOME_SUPERVISED=1` only after systemd shows restarts on exit 75 and 1. On Linux, once the units are written, install refuses and starts nothing when systemd doesn't show the host's unit loaded with this directory as its working directory, or doesn't restart the host on exit 75 and 1. The macOS agent always gets it, since its `KeepAlive` restarts the host on any nonzero exit.
- Run again, install writes the units again and restarts them. On Linux it enables them to start at boot. A manager failure after the units are written can leave them written or already restarted, and install says what failed.
