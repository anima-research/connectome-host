- `connectome service install [<recipe>]` writes and starts this install's resident service, then checks it. Linux gets `~/.config/systemd/user/connectome-<name>.service`; macOS gets `~/Library/LaunchAgents/com.animalabs.connectome.<name>.plist`. The name comes from the working directory that holds `.env`. The service runs `start.js` there with the recipe, an explicit PATH, and the data directory from `install.json` as `DATA_DIR`. It records the service in `connectome-host/service.json`. `connectome` shows its log, stop, and start commands.
- Service installation requires setup's install record to be bound to this working directory. For an unbound legacy, moved, or copied record, run `connectome setup discord` to confirm its recorded places first. A service record naming another directory also needs an explicit recipe to replace it. If its old directory remains, install leaves that directory's recorded units alone. If it is absent, install refuses replacement until the old unit files are removed and their native units are absent or unloaded. A failed directory or native-state query refuses replacement.
- A recipe whose source names a shell client or shell setting gets a localhost daemon when `term-sessions-mcp` is installed. Install stores or reuses `SESSION_SERVER_PORT` and `SESSION_SERVER_TOKEN` in `.env`, picking a free port from 3100 when needed. The token stays off the daemon's command line, and a token-bearing `.env` is made readable by its user alone. A replacement recipe without those source names retires the recorded daemon after the replacement host passes its checks. Cleanup removes only settings this service recorded writing, while their values still match. The output explains retained settings and how an explicit recipe can request the daemon again.
- Install checks the recipe with its planned service settings before replacing service files. Linux requires lingering and prints the root command when it is off. Its host unit gets `CONNECTOME_SUPERVISED=1` only after systemd shows restarts on exit 75 and 1. The macOS agent always gets it, since its `KeepAlive` policy restarts the host on any nonzero exit. Install waits up to a minute for the host to answer, matches its PID to the manager's main process, checks the running units, and quotes process reports separately from its own findings. A log excerpt that shows its last 40 lines reads back only as far as those lines and the lines before them that a secret could have begun in. A file-log excerpt reports the bytes before it. Current known secret values, including the shell token, are masked. Older or unrecorded credentials can remain.
- Invalid recipe or `.env` input and a command run inside the service are refused before service files change. A same-named unit belonging to another install blocks install. On Linux, another loaded service unit whose working directory is this one also blocks it. An unrelated unit can use another working directory. On macOS, install scans the user's LaunchAgents for another label naming this directory, including installed agents that are unloaded. Uncheckable agents produce a warning. Same-directory service commands exclude one another and say to wait and repeat when busy. Reinstall keeps the recorded recipe unless another is given. It restarts the resident and any shell daemon on Linux, or unloads and reloads their agents on macOS. Finish ongoing turns and shell work before reinstalling. Linux install enables the units to start at boot. Late ownership conflicts or manager failures can leave written files or units already restarted. The command reports what failed.
- `connectome service stop` stops the recorded host and shell without disabling the service. It reports whether the service starts again at boot or login and what a pending update means for the next start. `connectome service start` leaves running units alone, starts the stopped recorded units, waits for the host, and checks again. Both check ownership before acting. A service record naming another directory supplies neither command's targets nor status/check logs. A macOS launch agent stops when its user logs out of the graphical session, rather than when an SSH session ends.
- Where `launchctl list` exits with a status other than 0 or 113, the check `connectome service install` and `connectome service start` make once the host is started says that whether launchd has the agent loaded can't be told, with launchctl's own failure.
