- `connectome doctor` checks an install whole and says what's wrong. Run as root on an install another user owns, it stops at once and says to run it as that user, as install does. Otherwise it checks its service, which it finds by the unit names `connectome service install` derives for the directory, reading the recipe and working directory from the host's unit file or plist (no unit file is no service installed; a unit file whose start line or working directory line install couldn't have written, one whose working directory isn't the install's, or one doctor can't read, is a problem naming it; a shell daemon's unit file of the install's name whose working directory isn't the install's is a problem naming it too, since install refuses it whatever the recipe, and the service check leaves that unit out; a unit file it can't look at is said as that, not as gone; a service whose units are all inactive, or all unloaded under launchd, is said as stopped, and isn't a problem, with the command that starts it when no host answers; a service that runs while no host answers is said to have a host that may still be starting, to check again in a minute; a unit whose last start systemd skipped for a condition its unit or a drop-in sets is a problem, which names `systemctl --user status`; a host that answers while its service is stopped, or while it runs with a pid other than its main process, is a problem, since a host the service starts would take this install's socket from it) and where to read a unit's log, quoting none of it (under systemd, `journalctl --user -u` and the unit, for a unit that isn't active as it should be or has restarted; under launchd, the log file's path, for an agent loaded but not running), whether a host answers, whether the recipe the service runs loads, in the environment its host gets (from systemd's user manager, or from launchd for each name doctor reads or withholds, a name a dotenv value puts in and NODE_ENV among them, and from Bun; with no service installed, from the manager a service installed here would run under; with what the service's unit or plist sets, PATH and DATA_DIR among them, over the manager's, read as systemd last loaded the unit or as the plist is on disk, which a running host may not have, as doctor says), and fits the model's window (where the running host can count the system prompt and tools it sends, with `count_tokens`, for the model and budget the recipe gives it, and runs the recipe as it loads now, by that count, saying about how much is left for the reply and for what modules add at each turn, and, when that's less than agent.maxTokens, that a reply that long wouldn't fit in what's left; otherwise by estimate, as at load), whether `count_tokens` counts with the model the context's makeup is counted with and with the compression model, which servers aren't connected, with closed tabs said apart, the resident's shell's real call, which secret in setup's list of stored secrets the service gets no value for, from a file Bun reads, its unit or plist, or its manager, or gets empty, or doctor finds no server given and the recipe names nowhere else, and Discord: the token, the Message Content intent, the channels the bot can see, marking each text, announcement, voice or stage channel among them where it can't send, and the scope, by name and id; such a channel that the scope names is a problem. A recipe, or its system prompt, fetched from a URL that doesn't answer within a minute is a problem, and the checks go on. Then, for a service under systemd that runs it in the install's directory, with python3 there and the data directory known, it shows `scripts/connectome-doctor`'s ladder of where an incoming message got to, and counts the ladder's findings with its own: each about something wrong now is a problem, and each about what the ladder can't see, or the resident's own sleep, is a line. It replaces the values of the secrets setup stored, of the provider credentials and of the Discord bot token, as .env, the service's environment as doctor reads it (a value from a file its unit names isn't read, which doctor says) and its own environment hold them, and a Discord server entry's own token, where the recipe loads, the token also as it's sent to Discord, without a `Bot` or `Bearer` prefix and trimmed, with their names in what it prints, the ladder's lines included. With no stored-secrets list it says so, and replaces the value of every other name `.env` holds too, marking each line where it did as not a command to run. When it can't read which values are secret, as when the service's manager can't be asked or Bun doesn't read the service's environment within a minute, it prints only the install and why, with what values it knows replaced and what to do next, and stops. With no service installed, a manager it can't read is said instead, and the checks go on. It exits 1 when a check finds a problem. The host takes one client at a time, so doctor's connection to it closes another command's, as its help says.
- `connectome doctor` reads the install's `logs/failures.log` whole, wherever its service runs, and names each channel the subscription GC auto-closed, from the latest `subscription-gc-close` record for it: when it closed, how to reopen it, and how to stop it closing again, and says how many lines naming a close it couldn't read as one. It isn't counted as a problem.
- `connectome doctor` asks the running host for its counts of each agent's model calls (the `panel-request` op `health`). A turn whose model call failed is a problem, with when it failed, how many failed in a row, and where to find each failure's reason: the host's stderr, in a line that starts `[inference-failed] agent=` and the agent's name, which a service keeps in its log. Refusals are a line: how many since the host started or last switched session, the last one's time, and its category where that is one short word. A further line says when the newest turn met a refusal, since the counts don't show whether a retry in that turn then answered. A refusal is never counted as a problem, so a resident refused on every turn shows its refusals and no problem for them. The recipe's agent always gets a line, and another agent only with a failed turn or a refusal. When the counts list no agent by the recipe's name, that line says so, and the closing line says that agent's model calls weren't checked. No failure's text is printed.
