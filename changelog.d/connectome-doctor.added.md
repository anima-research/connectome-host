- `connectome doctor` checks an install whole and says what's wrong: its service (a service whose units are all inactive, as `connectome service stop` leaves them, is said as stopped, and isn't a problem, with the command that starts it when no host answers; a unit whose last start systemd skipped for a condition its unit or a drop-in sets is a problem, which names `systemctl --user status`; a host that answers while its service is stopped, or while it runs with a pid other than its main process, is a problem, since a host the service starts would take this install's socket from it) and its log (under systemd, the journal's lines from the first minute of a running unit's latest start, or the last lines of a start that ended; under launchd, the last lines of the host's log file, which can hold earlier loads), whether a host answers, whether the recipe the service runs loads, in the environment its host gets (from systemd's user manager, or from launchd for each name doctor reads or withholds, a name a dotenv value puts in and NODE_ENV among them, and from Bun; with no service record, from the manager a service installed here would run under; with what the service's unit or plist sets, PATH and DATA_DIR among them, over the manager's), and fits the model's window (where the running host can count the system prompt and tools it sends, with `count_tokens`, for the model and budget the recipe gives it, and runs the recipe as it loads now, by that count, saying about how much is left for the reply and for what modules add at each turn, and, when that's less than agent.maxTokens, that a reply that long wouldn't fit in what's left; otherwise by estimate, as at load), whether `count_tokens` counts with the model the context's makeup is counted with and with the compression model, which servers aren't connected, with closed tabs said apart, the resident's shell's real call, which secret in setup's list of stored secrets the service gets no value for, from a file Bun reads, its unit or plist, or its manager, or gets empty, or doctor finds no server given and the recipe names nowhere else, and Discord: the token, the Message Content intent, the channels the bot can see and the scope, by name and id. A recipe, or its system prompt, fetched from a URL that doesn't answer within a minute is a problem, and the checks go on. Then, for a service under systemd, with python3 there and the data directory known, it shows `scripts/connectome-doctor`'s ladder of where an incoming message got to, and counts the ladder's findings with its own: each about something wrong now is a problem, and each about what the ladder can't see, or the resident's own sleep, is a line. It replaces the values of the secrets setup stored, of the provider credentials and of the Discord bot token, as .env, the service's environment and its own environment hold them, and a Discord server entry's own token, where the recipe loads, the token also as it's sent to Discord, without a `Bot` or `Bearer` prefix and trimmed, with their names in what it prints, the ladder's lines included. With no stored-secrets list it says so, and replaces the value of every other name `.env` holds too, marking each line where it did as not a command to run. When it can't read which values are secret, as when the service's manager can't be asked or Bun doesn't read the service's environment within a minute, it prints only the install and why, with what values it knows replaced and what to do next, and stops. With no service record, a manager it can't read is said instead, and the checks go on. It exits 1 when a check finds a problem.
- `connectome doctor` reads the install's `logs/failures.log` whole, wherever its service runs, and names each channel the subscription GC auto-closed, from the latest `subscription-gc-close` record for it: when it closed, how to reopen it, and how to stop it closing again, and says how many lines naming a close it couldn't read as one. It isn't counted as a problem.
